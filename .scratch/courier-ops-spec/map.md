# Own-fleet courier delivery system — spec

## Destination

An implementation-ready spec for an own-fleet courier delivery system, covering three surfaces — a **web dispatcher console**, a **React Native driver app**, and a **React Native customer app** — with live map tracking of in-progress deliveries as the central feature. The spec lands at `.scratch/courier-ops-spec/spec.md` and is the deliverable; no production code is written during this effort.

## Notes

- **Domain:** own-fleet courier operations for a fresh/processed meat business. One business, its own drivers. Not a marketplace. Customers *do* place orders in the customer app (choose items, get them delivered) — reopened from an earlier out-of-scope call; see ticket 01.
- **Market & currency:** the business operates in the **Philippines**. All money is **Philippine pesos (PHP, ₱)**, stored as a whole number of **centavos** (1 ₱ = 100 centavos) — never a decimal fraction. Weights are metric (grams / kilograms). Confirmed during ticket 27.
- **Actors:** dispatcher (web), driver (React Native), customer (React Native). Customers are repeat accounts, so requiring an app install is acceptable.
- **Dispatch model:** manual assignment by a human dispatcher. A driver may hold multiple Deliveries at once (reopened from "one job at a time" during ticket 01 — see `docs/adr/0001-multi-stop-dispatch.md`); no route optimisation or ETA prediction is introduced by this.
- **Fixed constraint:** TypeScript everywhere — both RN apps, the dispatcher web app, and the backend runtime. Everything else on the stack is an open decision.
- **Driver app is permanently internal** (ticket 20): company-owned, MDM-enrolled devices, never store-published. Store-review reasoning is deleted for the driver binary, not deferred; OS/library constraints (foreground-service notice, Always permission, Transistorsoft release-build license) remain.
- **MVP is Android-only** across both mobile apps (ticket 20). iOS is a deferred fast-follow — **iOS decisions already made stay in the spec, marked post-MVP, not deleted**. Customer app remains a public Play Store app; the two-app split survives (it's a customer-binary Play-policy constraint).
- **Build the MVP as a forward-compatible subset** (ticket 20): the customer-app launch axis (pilot → public) and platform axis (Android → iOS) must stay additive, not forks. Guardrails: Play closed-testing track for any customer-app pilot (promotable to production, same signing key); a settlement-ready Order model (payment as a future independent track); no core shortcuts a "friendly pilot" tempts.
- **One dispatcher for the MVP** (ticket 37). Guardrail, per ticket 20's forward-compatible-subset rule: the **write path stays correct for many dispatchers; only the interface may assume one.** A second dispatcher is an additive change, never a fork. This also means dispatcher headcount never goes to the business owner.
- **Vendor licence terms are a first-class constraint** — three tickets in this map (17, 19, 41) found one late. Standing rules now settled: Mapbox geocode calls **must** set `permanent=true` or nothing may be stored (§2.7.2, zero-day cache); **Search Box is unusable** (no permanent mode at any price); **no Directions/Navigation output may ever be persisted**, at any tier, with no paid unlock (§2.10.1); **raw lat/lng may not be displayed to end users** (§2.7.1(b), §2.7.3(iv)) — a constraint on the dispatcher and any admin surface. The operative text is the **Product Terms** PDF, not `legal/tos`, which has no storage clause at all. See ticket 41.
- **Plan, don't do.** This map produces decisions, not deliverables. Tickets resolve questions; the spec is written at the end from the answers.
- **Skills every session should consult:** `/grilling` and `/domain-modeling` by default; `/research` for research tickets; `/prototype` for prototype tickets.
- **Tracker:** GitHub Issues in `vgviscayno/delivery-app` — see `docs/agents/issue-tracker.md`. This map is issue [#45](https://github.com/vgviscayno/delivery-app/issues/45), labelled `wayfinder:map`; tickets are issues #1–#44, all linked to it as GitHub sub-issues. Ticket type is the `wayfinder:<type>` label (`grilling`/`research`/`prototype`/`task`), a claim is an assignee, and status is the issue's open/closed state. Blocking uses GitHub's native issue dependencies (31 edges), not a text line; a ticket is unblocked when it has zero open blockers (`issue_dependencies_summary.blocked_by == 0`).
- **Two humans, not one.** Most tickets are settled by the dev in session. Some turn on facts or
  calls only the **business owner** can make — headcount, working hours, what staff may be told.
  Those are written up as a plain-language document under `questions/`, linked from the ticket,
  and the ticket is parked — assigned, with an `Awaiting:` note — so no session picks it up
  while it waits. Instances so far: ticket 34 (answered), ticket 43.
- **Domain docs:** this repo is single-context. Terms settled during grilling belong in a root `CONTEXT.md`; architecture decisions belong in `docs/adr/`. Both are created lazily by `/domain-modeling` — don't scaffold them upfront.

- [Backend platform options for realtime location](https://github.com/vgviscayno/delivery-app/issues/4) — nine options priced against a shared anchor (~2.5M writes/mo, ~$1–56/mo spread). **Message count, not connection count, is the cost driver**; only Supabase and custom-Postgres have a current geospatial story; only Ably solves reconnect continuity. No winner picked — that's ticket 05.
- [Backend platform decision](https://github.com/vgviscayno/delivery-app/issues/5) — **Supabase** (Postgres + PostGIS + Realtime + Auth + Storage). Geospatial requirement and fail-closed RLS auth over live location data ruled out every alternative, including a custom server; see `docs/adr/0002-supabase-backend-platform.md`.
- [Map provider for React Native and web](https://github.com/vgviscayno/delivery-app/issues/2) — **Mapbox**: `@rnmapbox/maps` on native, `mapbox-gl` on web, sharing a style JSON. $0 at this scale. No SDK shares components across native and web, so the dispatcher map is a separate implementation regardless; a shared `interpolatePosition` module is required because no SDK animates markers usefully.
- [Background location capture on the driver app](https://github.com/vgviscayno/delivery-app/issues/3) — `react-native-background-geolocation` (Transistorsoft) on an Expo dev-build, chosen for offline SQLite buffering and force-quit survival; live means **~10–15s while moving, with 30–120s gaps assumed**. Play policy forces the driver and customer apps to be separate binaries.
- [Domain model and delivery lifecycle](https://github.com/vgviscayno/delivery-app/issues/1) — vocabulary is **Order** (commercial transaction) + **Delivery** (courier unit, exists from Order submission). Delivery has two independent tracks: prep status (`Received → Preparing → Ready`) and courier status (`Unassigned → Assigned → Picked up → Delivered → Disputed → Closed`, plus `Cancelled`). Reopened two scope items: customer order-taking, and multi-stop dispatch (`docs/adr/0001-multi-stop-dispatch.md`). Full glossary in root `CONTEXT.md`.
- [Realtime transport and fan-out](https://github.com/vgviscayno/delivery-app/issues/6) — **Push via Supabase Realtime Broadcast** (not Postgres Changes), decoupled from a persisted "latest position" row per driver. Single-position ingest through one Edge Function with server-side rate limiting (~5s floor). Customers subscribe per-**Delivery**; the dispatcher subscribes to one global "all-drivers" channel instead of per-Delivery, avoiding duplication when a driver holds multiple concurrent Deliveries. Reconnection is latest-position-only for both actor types — no missed-message backfill.
- [Location cadence, staleness, and client smoothing](https://github.com/vgviscayno/delivery-app/issues/7) — ~~tracking scoped to an active Delivery~~ **amended by [ticket 34](https://github.com/vgviscayno/delivery-app/issues/34): capture runs while the driver is `on duty OR holding a non-terminal Delivery`**; distance-filter (~40–50m) while moving with a 60s stationary heartbeat; ~75m accuracy cutoff enforced server-side; `interpolatePosition` does straight-line interpolation with no extrapolation (freezes on a late fix); three-tier staleness UI (Live <90s / Stale 90s–3min / Lost >3min); current position only, no historical trail.
- [Monorepo layout and code sharing](https://github.com/vgviscayno/delivery-app/issues/8) — **one repo, pnpm workspaces + Turborepo**; shared `packages/domain`, `packages/api-client`, `packages/map-shared`, `packages/config`. No shared RN UI between driver and customer apps; dispatcher web is standalone React+Vite, no React Native Web. Types sync via Supabase-generated types with a hand-written domain layer on top. MVP demo ships as side-loaded Expo dev builds, no store submission yet.
- [Auth and identity across three surfaces](https://github.com/vgviscayno/delivery-app/issues/9) — **one Supabase Auth instance**, role column on `profiles` distinguishes dispatcher/driver/customer. Customer: email+password. Driver: dispatcher-provisioned, soft-deactivated. Dispatcher: flat role, no admin tier. Security crux (customer sees a driver's position only during their own active Delivery) is an `EXISTS` RLS subquery keyed to `courier_status`, fail-closed by default. Long sessions for driver/customer, idle-timeout for dispatcher; token refresh backstopped by ticket 03's offline buffering.
- [Customer live-tracking screen](https://github.com/vgviscayno/delivery-app/issues/14) — **split map/status panel** layout (prototype variant B), driver+pickup+dropoff+own-location markers with no trail, camera continuously follows with pan-to-release, progress shown via status label + hero straight-line distance + compact stepper (no ETA, ever), staleness freezes the panel in lockstep with the marker, unassigned state is map-less, driver contact is real-number tap-to-call.
- [Location history storage and retention](https://github.com/vgviscayno/delivery-app/issues/10) — **no server-side location history is persisted at all, for MVP.** Only an ephemeral current position exists (unchanged from ticket 06); no breadcrumb table, no retention window, no data-subject-request flow, since nothing is stored to retain or delete. Accepted trade-off: a dispute with no proof-of-delivery record leaves nothing to check afterward. Surfaced a small candidate addition to ticket 14 (a live connector line to the dropoff pin) — noted there, not decided.
- [Proof of delivery capture and storage](https://github.com/vgviscayno/delivery-app/issues/11) — **mandatory photo** (signature/recipient name optional), uniform across all Deliveries. Optimistic close: `Delivered` fires immediately, photo uploads in the background. Compressed on-device before upload. Private Supabase Storage bucket, signed URLs gated by ownership (same fail-closed pattern as ticket 09). **30-day retention, auto-deleted** — this is now the only artifact that survives a dispute, since ticket 10 keeps no location trail. Geo/time-stamp recorded but not trusted or server-verified.
- [Push notification pipeline](https://github.com/vgviscayno/delivery-app/issues/12) — **Expo push service**, single overwritable token per user, sends triggered by a **Postgres trigger on `courier_status`** (not application code). Customers get only `Picked up` and `Delivered` (no proximity push in v1). Drivers get new-assignment and reassignment/cancellation, **non-optional**, but fire-and-forget with no retry — the dispatcher console and driver's own list are the reliability backstop. Generic lock-screen-safe payload text; token cleared on driver deactivation.
- [Dispatcher console layout](https://github.com/vgviscayno/delivery-app/issues/15) — **map-dominant with a floating job-queue/suggested-drivers drawer** (prototype variant A), rejecting a drag-to-assign three-pane layout and a table-first/keyboard layout. Assignment is two clicks: select job → Assign next to a distance-ranked driver. Job age drives a three-tier attention badge; a driver locked by another dispatcher's in-flight assignment shows a named lock pill. Driver-clustering-at-scale and the concurrent-assignment locking mechanism were not exercised by the prototype — carried to Not yet specified.
- [Location library licensing and the when-in-use alternative](https://github.com/vgviscayno/delivery-app/issues/17) — Transistorsoft's license is **$399 one-time** (single app, perpetual, keeps working if the update subscription lapses) — not a reason to reopen ticket 03. `CLBackgroundActivitySession` genuinely avoids the Always-permission dance under iOS 17+, but neither candidate library exposes it; adopting it means owning a custom native Swift module. Ticket 03 stands unchanged; ticket 16 keeps its current scope with a forward-looking note about this as a future de-risking path.
- [Driver-app distribution model and MVP platform scope](https://github.com/vgviscayno/delivery-app/issues/20) — **driver app permanently internal** on company-owned MDM Android devices; **MVP is Android-only** (both mobile apps), iOS a retained-but-deferred fast-follow. Store-review reasoning deleted for the driver binary; OS/library constraints kept. MDM pre-provisions permissions where it can, app keeps the runtime safety net. Customer app stays public Play, two-app split survives. **Build the MVP as a forward-compatible subset** (pilot→public and Android→iOS additive, not forks). Amends tickets 03/08/16; spawned research tickets 18, 19.
- [Customer-app launch mode decision](https://github.com/vgviscayno/delivery-app/issues/21) — client picked **Option A, controlled pilot** via Play closed-testing track, cleanly (no hybrid/sequencing caveat). Payment stays out of scope; no new tickets needed — ticket 20's guardrails already cover this case.
- [Driver location permission onboarding](https://github.com/vgviscayno/delivery-app/issues/16) — **hard block**: a driver can't be assigned or start a job without Always granted. Requested upfront at login, re-verified at first job assignment; When-In-Use grant is immediately followed by a deep-link to Settings (not Apple's own deferred prompt) to reach Always. Mid-shift downgrades are caught via the library's authorization-change listener — an in-flight job is never yanked, only forward-looking assignment is blocked, and the dispatcher console gets a distinct real-time flag. Android bundles background-location + OEM battery-exemption requests proactively into the same onboarding flow. Foreground notification only shows during an active Delivery, named to the job. One shared explanation string serves both the in-app screen and the store usage-description. No nagging: backs off to a persistent banner after the first dismissed prompt, resurfacing full-screen only when a blocked action is attempted.
- [Android MDM provisioning for the driver fleet](https://github.com/vgviscayno/delivery-app/issues/18) — **background location IS MDM-grantable, but only on a fully-managed (Device Owner/COBO) device** (`PermissionPolicy: GRANT`, no prompt) — the "Android 12+ blocks MDM auto-grant" claim only applies to Profile Owner/work-profile enrollment. Deletes ticket 16's interactive Android permission dialogs. OEM battery-optimization exemption has **no MDM lever at all**; moves to a one-time kitting-checklist step instead of driver-facing onboarding. Foreground-service notification and downgrade detection unaffected either way. Distribution: **managed Google Play private-app** (not direct APK push); tooling: fully-managed enrollment via a small third-party EMM console wrapping the Android Management API. Amends ticket 16.
- [Transistorsoft licensing for an Android debug-build pilot](https://github.com/vgviscayno/delivery-app/issues/19) — **yes**, the pilot can run fully unlicensed on Expo dev builds (SDK is "fully functional in DEBUG builds" per Transistorsoft's own docs, just a harmless log warning). The $399 triggers on Android **build type** (debug vs. anything else), not distribution channel — **no internal/fleet carve-out**, a company-internal release build owes the license exactly like a Play Store release. Guardrail: the stock, unmodified `development` profile in `eas.json` is what routes the build to `assembleDebug`; hand-editing `gradleCommand`/`buildType` on that profile would silently flip it to release and trip the gate. Android-only-now costs nothing extra versus buying the iOS key later (same $399 Starter tier, both keys included).
- [ETA feasibility at zero cost](https://github.com/vgviscayno/delivery-app/issues/24) — **a genuinely zero-cost path exists: the non-routing heuristic** (haversine distance × circuity-factor correction ÷ assumed average speed, evolving into a historical-average-per-distance-bucket model), free by construction with no vendor ceiling. Mapbox Directions' free tier (100k req/mo) would also plausibly cover this business's volume (5x–300x headroom) but is "free today," not free by construction. Self-hosted OSRM is free to license but not to run (~$20–60/mo + real maintenance burden) — not recommended. Doesn't itself decide whether to reopen ticket 14 or the Out-of-scope ETA line — see new ticket 25.
- [Order-acceptance time window](https://github.com/vgviscayno/delivery-app/issues/22) — per-day-of-week `store_hours` + `store_closures` for holidays; enforced as a customer-app UI gate backed by a server-side guard at Order-submission (never trusts client clock), browsing always allowed, checkout blocked outside the window. New custom settings UI in the dispatcher console (first admin surface in the app) manages hours; global 15-minute last-call buffer before close; hard re-validation at submit with no grace period for mid-checkout. Pure gate in front of Order submission — no new domain concept.
- [Order-acceptance location radius](https://github.com/vgviscayno/delivery-app/issues/23) — **road distance**, not straight-line, via **Mapbox Directions** free tier (reusing ticket 24's finding), checked against the customer's delivery address — this deliberately reopens the routing-engine question for the radius check specifically, distinct from the still-open ETA question (ticket 25). Radius is admin-configurable alongside `store_hours` (ticket 22's settings surface); the store's own fixed coordinates are a new `packages/config` value. Client pre-check at address entry (blocks saving an out-of-radius address, shows how far over) plus a server-side backstop at Order-submission, fail-closed like tickets 09/22.
- [Product catalog domain model & dispatcher management](https://github.com/vgviscayno/delivery-app/issues/26) — adds **Product** + **Category** (many-to-many, ordering on the join) to `CONTEXT.md`. Product uses a **stable id + snapshot** model (Orders copy name/price at submission; catalog edits never rewrite placed Orders — `docs/adr/0003`). `price_type` is a two-value discriminated union (`per_unit` → `unit_price`; `per_weight` → `price_per_kg` + per-Product `weight_step_grams`, which is also the minimum) — **this is what ticket 27 builds on**. Availability is a manual toggle (no stock). CRUD lives on ticket 22's settings surface; soft-delete. In-flight carts re-validate at ticket 29's checkout gate, no live subscription. Photo presentation + by-weight input shape deferred to ticket 30.
- [ETA display decision](https://github.com/vgviscayno/delivery-app/issues/25) — **no ETA shown to customers in the MVP.** "If free" turned out to mean "if free *and* it causes no problems," and the only free-by-construction option (ticket 24's heuristic) is too rough — a shown *time* reads as a promise where ticket 14's hero straight-line *distance* reads as "roughly close." Ticket 14 stands unchanged (no ETA, ever). Feature is **paused, not killed**: an *accurate* ETA (Mapbox Directions, plausibly multi-stop-aware) is a live post-MVP candidate. Settles the map's Out-of-scope ETA line — see below.

- [Order pricing model: provisional → final packed-weight record](https://github.com/vgviscayno/delivery-app/issues/27) — an Order's price is **provisional at submission → final at packing**; `docs/adr/0004`. **Uniform totals, discriminated inputs**: every line carries `provisional_total`/`final_total`/`money_delta` (a per-unit line is set final-at-submission with a zero delta), while only the *inputs* follow ticket 26's `price_type` union. Per-weight lines add estimated/packed/delta grams + a captured `tolerance_grams`. **`Ready` now means packed *and* priced** — it can't be reached until every per-weight line has a packed weight. Record freezes at `Picked up`; corrections before that append to a small log. Money is whole **centavos (₱)**; per-kg rates are never converted to per-gram. **Delivery fee** added: flat for MVP, captured at submission, stored *beside* the goods totals (distance-based later is additive). User settled the tolerance rule — **per-Product `tolerance_grams`, default 250 g, symmetric, per line, burden on the shop** — which **amends ticket 26** and is handed to ticket 28 as settled. Settlement boundary drawn explicitly: record the delta, never act on it.

- [Packed-weight re-pricing approval flow & lifecycle](https://github.com/vgviscayno/delivery-app/issues/28) — a tolerance breach puts the Order into **pending Price approval**, blocking `Ready → Picked up` until a **dispatcher phones the customer**; `docs/adr/0005`. No in-app approval screen and no third push event (ticket 12's pipeline has no retries). Modelled as a **transition guard, not a new lifecycle state** — the first rule coupling the prep and courier tracks, so `CONTEXT.md` now names it. **Shortfall gates exactly like an excess** (`abs(delta) > tolerance`); only the dispatcher's script differs. Customer has three answers: approve, **decline the breaching lines and keep the rest** (partial continuation — lines are **soft-removed**, never deleted; only breaching lines may go, nothing may be added), or reject, which cancels in the same action. Declining every line *is* that cancellation. **No timeout** — an unanswered call holds indefinitely, a human cancels. A weight corrected after approval **voids and re-evaluates** it. Record is a dispatcher assertion: outcome, who, when, approved-total snapshot, optional note. Delivery fee never moves. Pre-authorization at checkout rejected for MVP. `CONTEXT.md` gains **Price approval**, **Removed line item**, and a definition of **Excess / Shortfall** — which the glossary had been using undefined since ticket 27.

- [Cart & checkout assembly flow](https://github.com/vgviscayno/delivery-app/issues/29) — **one screen**, not a cart→checkout pair: lines stay editable alongside the address selector, fee breakdown, and Submit, because per-line gate rejections have to be fixable where they render. Cart is **persisted locally** per user (no server cart), **refreshed one-shot on open** (not ticket 26's rejected live subscription). The gate stack is **two inherited gates, not three** — 28 killed checkout pre-authorization after this ticket was charted — so submit re-checks **store hours (22), delivery radius (23), line availability (26), and a price increase since the customer last saw it**; all four evaluated, **never fail-fast**, rendered by blast radius (whole-order banner → inline per-line). An unavailable line is **never auto-removed**; a price rise blocks and the acknowledgement is the second tap of Submit (a drop applies silently) — the pre-submission counterpart of `docs/adr/0005`, cross-referenced there. Submission is one Edge Function, one transaction, Order + Delivery or neither, guarded by a **client-minted idempotency key held per cart and rotated only on success**; then straight to ticket 14's unassigned tracking screen, no receipt. Address is *selected* from saved addresses (entry stays in fog). **Delivery fee value becomes a dispatcher-editable setting** on ticket 22's settings surface. No new terms, no new ADR. Widened ticket 30 to cover the cart screen; surfaced customer order history as fog.

- [Customer catalog browse & cart UX](https://github.com/vgviscayno/delivery-app/issues/30) — **variant B: category tabs over a 2-column photo card grid**, product opens a bottom sheet. By-weight input is **preset chips generated per Product from `weight_step_grams`** (so the smallest chip *is* ticket 26's minimum), with a `Custom…` chip revealing a stepper — variant A's control survives as the uncommon path. **The same chip row is the control on the cart line**, which is what this ticket existed to guarantee. `photo_url` **stays nullable** — a photoless Product renders the **store logo mark** at photo dimensions, so card height never varies and ticket 26 needs no amendment. Price display confirmed: per-unit flat, per-weight as a **rate** (`₱1,150/kg`, never a total), `~` on every estimate everywhere. Tabs also mean a Product in two Categories is never seen twice in one scroll. Running total is a floating cart button (goods only; fee broken out at checkout). **Settles the density ticket 29 left open**: whole-order banners **collapse to one line each, tap to expand** — all failures stay simultaneously visible, blast-radius order untouched, but the all-four state drops from ~200px to ~129px so line items are reachable without scrolling. Per-line failures stay inline and uncollapsed. No new terms, no ADR.

- [Dispatcher packing and price-approval screen](https://github.com/vgviscayno/delivery-app/issues/31) — **a full-screen packing bench** (prototype variant B), its own mode beside Dispatch rather than a panel in ticket 15's drawer; the map is gone while packing, and ticket 15's console is otherwise untouched. **Information inline, decision at the gate**: no per-line alarm while weighing, only a muted `outside ±250 g` footnote in the Delta column, because the shop is *sometimes one person and sometimes two* — an immediate alarm would invite the packer to adjust the weight until it stops. The blocked `Ready` press opens a **review sheet** carrying the itemised provisional-vs-final figures, checkboxes on breaching lines only, the fee broken out as never-moving, a note field, and ticket 28's three actions. A's treatment won for the blocked `Ready` button: amber reason immediately beside it, not dim text across the footer. **Held Orders split out of the to-pack queue** into an `Awaiting price call` section — a different kind of work item, so its own list, with the waiting badge as the only pressure. No new terms, no ADR.

- [Saved delivery addresses, entry, and geocoding](https://github.com/vgviscayno/delivery-app/issues/33) — **the pin is authoritative**, always required; the written address is a caption, never a navigation target, because a PH address routinely isn't rooftop-resolvable. Entry is **search → confirm pin → details**, with **search skippable** ("drop a pin instead") since a flow requiring a successful geocode would fail a real share of customers. Ticket 23's radius check fires at **pin-confirm** and **persists no verdict** — recomputed statelessly at entry, at checkout selection, and at submit, per ticket 29's courtesy/rule split. The Order **snapshots the whole address**, recorded as an **extension to `docs/adr/0003`** rather than a new ADR, with one new argument: an in-flight Delivery must never have its destination moved, which makes edit and delete safe with no guard rules (delete is soft, like Product). Snapshot lives **on the Order**, beside ticket 27's delivery fee — what was charged for the trip and where it goes are one fact. **Closes a gap nothing had noticed: `contact_phone` on the Address is the only phone number in the system** — ticket 09's email+password meant the driver had no way to reach the customer at all. Dispatcher may edit **non-gating fields on one Order's snapshot only** (never the pin, never the saved record), the same narrow-exception shape as ticket 28. Driver gets tap-to-call and Navigate-to-pin; **nothing flows back** to the Address. `CONTEXT.md` gains **Address** and **Delivery address**. Spawned tickets 40 and 41.

- [Customer order history](https://github.com/vgviscayno/delivery-app/issues/36) — an **`Orders` tab that is the app's spine**, not an archive. Settles a gap nothing had noticed: **the customer app had no navigation shell at all** — 30, 29 and 14 each designed a screen and none said how to move between them. Now a three-tab bar (`Shop`/`Orders`/`Account`), cart stays ticket 30's FAB, tracking is pushed not tabbed; **`Account` becomes the home ticket 33 never named for saved Addresses**. **One list**: active Orders in a pinned section (**1..n — concurrent Orders are allowed**, explicitly not a sixth gate on ticket 29's stack), tapping through to ticket 14; cancelled Orders shown de-emphasised, never hidden. This closes ticket 29's no-receipt hole — a customer who backgrounded the app previously had **no route back to a live Delivery**. Row is text, reusing **ticket 14's status vocabulary verbatim** so the two surfaces never disagree. Detail shows the **full 27/28 money record, progressively disclosed** — deltas, removed lines, Price approval outcome — because the customer already had the phone call. Driver **name only, no number** post-delivery. Ticket 11's photo **is** customer-visible and its 30-day window **stays closed**: the image expires to a plain text line, the text record is retained indefinitely. Dispute gets a **seam and nothing more** (phone number, no `Disputed` transition from the app) — **depends on ticket 40** for the number. Re-order ruled out of MVP into fog. No new terms, no ADR.

- [Concurrent-dispatcher assignment locking, the real mechanism](https://github.com/vgviscayno/delivery-app/issues/37) — **no locking mechanism at all.** Ticket 15's lock sat on the **wrong noun**: ADR 0001 lets one driver hold many Deliveries, so same-driver contention breaks nothing — the only real conflict is two writers on one **Delivery**. Replaced by **optimistic concurrency**: the assignment write is conditional on `courier_status` still being `'Unassigned'`, and zero rows affected *is* the conflict signal. It holds nothing, so the ticket's lock-lifetime question and its interaction with ticket 09's idle timeout are **moot, not deferred**. MVP has **one dispatcher**, so ticket 15's named lock pill is **deleted** — but the condition survives its own justification, because a **customer** may cancel an `Unassigned` Delivery, making *assign-races-cancel* the live conflict. A zero-row write names the actual cause rather than showing one generic message. Scope: ticket 31's packing bench needs nothing (last-write-wins on a weight is fine); **Price approval gets the same conditional write** — an approved-total snapshot on a cancelled Order is a false record. No new terms, no ADR. Amends tickets 15 and 28.

- [May Mapbox geocoding results be stored permanently?](https://github.com/vgviscayno/delivery-app/issues/41) — **yes, but only if asked for explicitly: set `permanent=true` on every geocode call.** Mapbox Product Terms §2.7.2 forbid storing or caching a Temporary Geocode *for any period* — zero days, not the 30 people remember (§2.8.1's 30 days is map **tiles**, not Search). The restriction is gated on **request mode, not plan tier**, so ticket 33's record shape was non-compliant and leaving the free tier was never the fix. Permanent geocoding costs **$5/1,000, billed from request #1**, needing only **a card on file** — no enterprise contract, other free tiers survive; **~$5–15/month** at this volume. Ticket 33's shape then stands unchanged. One design casualty: **drop Search Box** — no permanent mode at any price — so ticket 33's search step must use **Geocoding v6 forward**. Hardens ticket 23: §2.10.1 bans storing **any** Navigation API result at **every** tier with **no paid unlock**, so storing no Directions output is a licensing requirement, not a preference. Adds a display rule: raw lat/lng may not be shown to end users (§2.7.1(b), §2.7.3(iv)) — check the dispatcher and admin surfaces. **Ticket 02's vendor choice is not in question.** Also worth knowing: `legal/tos` contains no storage clause at all — it all lives in the **Product Terms** PDF.

- [Driver shift and availability model](https://github.com/vgviscayno/delivery-app/issues/34) — **answered by the business owner**, then grilled for consequences. **Two drivers**, working day **08:00–16:00** (stock prep 06:00–08:00 before it; the 16:00 finish dodges rush hour), handsets **never go home**. Duty is an **explicit clock-in** — but the shop already runs an **HRIS**, so it is an *availability signal, not a time record*: modelled as an **On duty flag with no history**, named against "Shift" precisely because a `started_at`/`ended_at` entity attracts payroll features that belong to the HRIS. Drivers are **visible for the whole working day**, which **amends ticket 07** — capture is scoped to `on duty OR holding a non-terminal Delivery`, not to an active Delivery, finally making ticket 15's distance-ranked driver suggestions rest on data that exists. Duty **auto-ends server-side at 16:00 unless work is still held**, so a forgotten tap can't broadcast overnight and a 16:15 drop can't go dark. Off duty **warns**, it does not block — deliberately unlike ticket 16's Always-permission hard block, because permission is technically load-bearing while duty is a human signal that can be wrong, and with two drivers one forgotten tap would stop the shop. **No concurrency cap** (ticket 15's job count already is the advisory display); the ceiling the owner wants is **time**, not count — a **15:30 order cutoff**, which needs no new concept, just ticket 22's `last_order_buffer_minutes` at **30** and close at **16:00**. **No break state.** **Ticket 10 unaffected** — visible all day, recorded never. Amends **07, 16, 22, 39**; ticket 16's shared permission copy now states something **false** and must be rewritten. Adds **Driver**, **On duty**, **Ordering window** to `CONTEXT.md`. No ADR — nothing here is hard to reverse. Unblocks **32** and **39**; surfaces **42** and **43**.

- [Driver app screens and job flow](https://github.com/vgviscayno/delivery-app/issues/32) — **Variant C, map-led, one screen**: a map canvas with the held stops as pins, the job list and job detail as sheets over it, so the driver never loses spatial context to read an address. Ordering is **spatial and implicit** — the pins are the ranking, no manual reorder (route optimisation stays out of scope). Mirrors ticket 15's console, so one style JSON and one interpolation module now serve both maps. Surfaced and settled a **dispatcher priority flag**: one advisory boolean with a mandatory reason, capped at one per driver, clearing on terminal state, **no acknowledgement** — never a rank, which would be manual route optimisation by the back door. Rendered as a violet overlay so it composes with the in-van green and price-hold amber rather than replacing either. Console side is [ticket 44](https://github.com/vgviscayno/delivery-app/issues/44).

## Out of scope

<!-- ruled beyond the destination. Never graduates; returns only as a fresh effort. -->

- **Route optimisation** — a driver picks their own next stop by eyeballing straight-line distance; no engine computes an optimal order.
- **ETA prediction** — **out of v1, settled** ([ticket 25](https://github.com/vgviscayno/delivery-app/issues/25)). Reopened by client request, investigated (ticket 24), and decided: no ETA is shown in the MVP. The rejection was on *quality*, not the feature on principle — the free-by-construction heuristic was too rough, and "if free" meant "if free and problem-free." An **accurate ETA (Mapbox Directions, plausibly multi-stop-aware) is a live post-MVP candidate**, not a dead idea; it returns as a fresh effort starting from ticket 24's findings. Note: the routing-engine decision this line originally took off the map is **not fully out of scope regardless** — [ticket 23](https://github.com/vgviscayno/delivery-app/issues/23) independently committed to Mapbox Directions for road-distance radius checks. Only *ETA display* is out.
- **Payments and payouts** — no money moves through the system in v1. Note: pricing *shape* is specified in-scope and **now settled** (ticket 27 + `docs/adr/0004` — a provisional→final, settlement-ready Order record per ticket 20's guardrail). Only the *execution* of settlement stays out: charging the final total, refunds, authorization holds, any money movement on the packed-weight delta. **No field on the Order record states whether anything was paid** — a payments track adds its own rather than borrowing these. A **delivery fee** now exists as a captured *amount* on the Order (flat for MVP); charging it is out of scope like everything else.
- **Promotions, discounts, and coupons** — ruled out while charting the catalog/cart tickets (26–30). Reaches into the Order total and settlement record; edges toward payments. Never ticketed; returns only as a fresh effort.
- **Item substitutions** — out-of-stock → swap handling. Ruled out while charting the catalog/cart tickets; a manual availability toggle (ticket 26) replaces stock-driven substitution. Interacts with the packed-weight approval flow (ticket 28) and would balloon it. Never ticketed; returns only as a fresh effort.
- **Driver-map clustering and filtering-by-state** — carried as fog since [ticket 15](https://github.com/vgviscayno/delivery-app/issues/15), whose prototype ran legibly on 5 seeded drivers and never exercised clustering. It was fogged pending one number: how many drivers a dispatcher screen shows at once. [Ticket 34](https://github.com/vgviscayno/delivery-app/issues/34) supplied it — **two**. This is not unsharp any more, it is unnecessary; a clustering layer for two pins is dead weight. Returns only if the fleet grows, and then as a fresh effort.
- **Marketplace mechanics** — courier onboarding, job offer/accept, supply-demand matching. Drivers are employees, assigned by a dispatcher.
- **Kitchen/prep states** — this is a meat retailer, not a restaurant; there is no kitchen prep pipeline between order and dispatch.
- **Install-free tracking link for one-off recipients** ([ticket](https://github.com/vgviscayno/delivery-app/issues/13)) — no distinct recipient actor exists; the booking account holder is always the recipient, so there's nobody to serve an unauthenticated tracking link to. A plausible future feature (gifting, third-party recipients), but it returns as a fresh effort, not a resumption.
- **Post-submission order editing** — a customer changing an Order's contents at will after submitting it: adding lines, swapping products, increasing quantities, or dropping a line that packed perfectly. Ruled out during ticket 28. Every gate in the system — store hours (ticket 22), delivery radius (ticket 23), availability (ticket 26) — validates an Order once, at submission; editing would force all three to become re-runnable mid-flight. The one exception is deliberately narrow and stays in scope: **subtractive-only removal of lines that breached tolerance**, inside the approval call the shop itself initiated (`docs/adr/0005`). A customer wanting anything else gets a cancel and a fresh Order.
