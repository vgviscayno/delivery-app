# Courier Ops

Own-fleet courier delivery system for a Philippine meat shop: a web dispatcher
console, a driver app and a customer app over one Supabase backend.

`CONTEXT.md` is the glossary — the words in this repo mean what it says they mean.
`docs/adr/` holds the decisions of record. The MVP spec is issue #54.

## Layout

```
apps/console/        dispatcher console — React + Vite (deployed to Cloudflare Pages)
apps/driver/         driver app — Expo dev build, Android
apps/customer/       customer app — Expo dev build, Android
packages/config/     backend environment and the constants every surface shares
packages/domain/     hand-written domain types over the generated Supabase schema
packages/api-client/ the typed Supabase client and the named server surface
packages/db/         database tooling: migrations, gates, pgTAP, seed, type generation
supabase/            the Supabase project: migrations, pgTAP tests, seed.sql
scripts/             CI helpers
```

The mobile apps are React Native (ADR 0013) and run as dev builds, not in Expo Go,
because Transistorsoft and `@rnmapbox/maps` are native code. `android/` and `ios/` are
generated by `expo prebuild` from each app's `app.config.ts` and never committed.

## Getting started

Needs Node 22+, pnpm, and Docker running.

```sh
pnpm install
pnpm db:start          # local Supabase, migrations, seed
cp .env.example .env.local   # paste the API URL and anon key the CLI printed
pnpm --filter @courier/console dev
```

For a mobile app, with an Android emulator running:

```sh
cp apps/driver/.env.example apps/driver/.env.local   # the anon key, and a Mapbox pk. token
pnpm --filter @courier/driver android                # builds the shared packages, then the dev build
```

Metro reads the shared packages from their `dist`, so `start` and `android` build them
first, and `eas-build-post-install` does the same on EAS. EAS builds use the profiles in
each app's `eas.json`; nothing in `pnpm build` runs EAS or a native build. After
`eas init`, set `EAS_PROJECT_ID` in the app's `app.config.ts`: until then the app has no
update URL, so `expo-updates` is off and the driver `pilot` channel does nothing.

Sign in to the console as the seeded dispatcher, `dispatcher@courier.local` /
`dispatcher-demo`. The seed only ever runs against a local database, never production.

## Accounts and roles

One Supabase Auth instance holds every account. Each Auth user gets one profile in
`app.profiles`, created by a trigger in the same transaction: a role (`dispatcher`,
`driver` or `customer`), an active flag with its deactivation time, and one overwritable
FCM push token.

The role comes from `raw_app_meta_data`, which only the service role can write (the
Admin API, the seed, the driver invite). A sign-up through the public API is always a
customer, whatever it puts in its own user metadata.

The console asks `public.console_profile()` after every sign-in and on every reload. It
answers only for an active dispatcher, and the console signs anyone else straight back
out. The console also signs the dispatcher out after `VITE_DISPATCHER_IDLE_MINUTES`
(default 30) without activity in any of its tabs. That check runs in the browser
because Supabase's own inactivity timeout is a Pro-plan setting and would apply to
customers too.

### Adding a dispatcher

The role is copied into the profile once, when the Auth user is inserted. The
dashboard's **Add user** sets no app metadata, so an account made there is a customer,
and the console signs it straight back out. Give it the role afterwards:

1. In the Supabase dashboard, **Authentication → Users → Add user → Create new user**,
   with **Auto Confirm User** ticked. This account can change every shop setting, so
   give it a strong password.
2. In the **SQL Editor**, with the new account's email:

   ```sql
   update auth.users
   set raw_app_meta_data = raw_app_meta_data || '{"role": "dispatcher"}'
   where email = 'dispatcher@example.com';

   update app.profiles
   set role = 'dispatcher'
   where id = (select id from auth.users where email = 'dispatcher@example.com');

   select p.role, p.active, u.email
   from app.profiles p join auth.users u using (id)
   where u.email = 'dispatcher@example.com';
   ```

   The last query should return `dispatcher | true`. Setting the metadata as well
   keeps the Auth user agreeing with its profile, so nothing that reads the role from
   metadata later turns it back into a customer.

## Shop settings

The shop's rules are data the dispatcher edits on the console's Settings tab: the
Ordering window per weekday, closure dates, the Same-day cutoff buffer, the delivery
radius, the Delivery fee (whole centavos), the Shop phone (E.164), the QR Ph image, the
end-of-day time, the dark threshold and the Time confirmation morning cut-off. Any
signed-in account reads them through `public.shop_settings()`, `ordering_window()` and
`shop_closures()`. Only an active dispatcher can change them, and anon can do neither.

The migration sets the values the business has agreed on. The ones it hasn't (radius,
fee, Shop phone, open weekdays and hours, morning cut-off) start empty in production,
and the seed fills them with placeholders. The QR Ph image is kept in the private `shop`
Storage bucket. Every upload gets a new name, so a replaced image is never served from a
cache. The seed's placeholder image is uploaded by `[storage.buckets.shop]` in
`supabase/config.toml` on every local reset. On a preview database, run
`supabase seed buckets`. Like the seed, never run it against production.

## Catalog

The dispatcher keeps the catalog on the same Settings tab: Products, Categories, and
each Product's position within each Category it is in. Customers read it through three
views, `public.catalog_products`, `catalog_categories` and `catalog_memberships`. Those
views show only Products that are available and not deleted. The console reads the
whole catalog through `dispatcher_products()` and `dispatcher_category_products()`.
Every write is an RPC that only an active dispatcher may call.

A Product is priced per unit (`unit_price_centavos`) or per weight
(`price_per_kg_centavos`, `weight_step_grams`, `tolerance_grams`). A check constraint
makes sure each Product carries exactly the fields of its own price type. Prices are
whole centavos, and per-weight rates stay per kg. Deleting a Product is soft, so Orders
that refer to it keep working (ADR 0003). The production catalog starts empty. The seed
fills in a dozen placeholder Products across five Categories.

## The Shop clock

There is one clock, `app.now()`, and one time zone, `Asia/Manila` — the Shop clock in
`CONTEXT.md`. No
migration, RPC, view or trigger may call `now()`, `current_timestamp` or
`clock_timestamp()` directly — every time rule reads the clock, so every time rule can
be tested at its exact boundary by pinning it with `app.pin_clock()`.

Clients never work out a Manila date for themselves. They call
`public.server_clock()` and display what it says.

## The three gates

The first two live in the database (see the security harness migration), so CI and pgTAP
can never drift apart. `pnpm db:lint` runs all three.

**The RLS lint.** Any table in a PostgREST-exposed schema with row security off is
readable by anyone holding the anon key. `app.tables_without_rls()` finds them, and
CI fails on any row.

**The role × resource matrix.** `app.access_matrix` records, for every table, view and
RPC a client can reach, whether each of the four actors — `anon`, customer, driver,
dispatcher — may touch it, and why. `app.access_matrix_gaps()` is the completeness
check: it fails on an object nobody has ruled on, on a row left behind after an object
goes away, and on an `anon` row that contradicts the actual grants. Later tickets add
rows in a migration; they never edit the harness.

**Exposed schemas agree.** `app.exposed_schemas()` decides what the other two gates look
at, so a schema PostgREST serves but the harness does not know about leaves everything
inside it unguarded while both gates still pass. This one compares `api.schemas` in
`config.toml` against the harness and fails on a disagreement either way — the one
thing the database cannot check on its own.

## Environments and the release path

Two backends while on Supabase Free (ADR 0012): local and production. Free has no
branching, so ADR 0009's preview branch per PR waits for the move to Pro (#92).
Migrations reach production only through CI:

1. **The three gates and pgTAP**, in CI's `database` job on a local Supabase. This is
   the rehearsal;
2. **A dry run** — the `Migrate production` workflow, from `main`, with `push` off and
   the project ref typed out by hand. It lists the migrations production is missing in
   the job summary and applies none of them;
3. **The push** — the same workflow again with `push` on. It refuses unless a dry run
   succeeded on the same commit, then dry-runs again and pushes.

Each step checks the one before rather than trusting it. `scripts/check-rehearsed.mjs`
refuses a commit whose `database` job did not pass, and `scripts/check-dry-run.mjs`
refuses a push with no dry run behind it on that commit.

Merging a PR does not migrate anything.

The console deploys to Cloudflare Pages from `main` only, pointed at production. There
are no PR previews: with no preview branch to point one at, a preview would need
production, and a preview that can write to the shop's real data is worse than no
preview.

### Secrets CI needs

Secrets live on the `production` GitHub environment, not the repository, so production
credentials only reach jobs that run in `production`.

| Secret                                          | Used by                                   |
| ----------------------------------------------- | ----------------------------------------- |
| `SUPABASE_ACCESS_TOKEN`                         | production migration                      |
| `SUPABASE_PROJECT_ID`                           | production migration, typed confirmation  |
| `SUPABASE_DB_PASSWORD`                          | production migration                      |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY`             | console build (the publishable key)       |
| `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` | Pages deploy                              |

Plus the `CLOUDFLARE_PAGES_PROJECT` variable on the same environment.

`bash scripts/setup-supabase.sh` walks through creating the Supabase project and sets
every Supabase secret above. `bash scripts/setup-cloudflare.sh` does the same for the
Pages project and the Cloudflare values. On Windows, run both from PowerShell through Git
Bash (`& "C:\Program Files\Git\bin\bash.exe" scripts/...`): plain `bash` there is WSL's,
which has no Node for wrangler.

## Testing

A good test checks behaviour through the highest seam available and never checks
internals.

- **The server contract** — pgTAP, `pnpm test:db`. Most tests live here. Tests build
  their own data and roll back.
- **Package logic** — Vitest, `pnpm test`. No Docker, ever: the database work is its
  own workspace with its own task.

`supabase/seed.sql` is demo data for local and preview work. It is **never a test
input** — `pnpm test:db` resets with `--no-seed` first, so nothing in the seed can
quietly become the reason a test passes. It seeds again once the tests finish, pass or
fail, so the console can still sign in to the local database afterwards.
